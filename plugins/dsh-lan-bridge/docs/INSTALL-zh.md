# dsh-lan-bridge 安装与使用（中文）

把同一局域网里的电脑接起来：一端是 **Agent 侧**（它的 AI 获得对其他机器的文件编辑与 Shell 执行工具），另一端是 **桥接侧**（它把自己的文件/命令能力按授权开放出去）。连接时 Agent 侧自动解锁 6 个远程工具，断连时自动回收——**对话上下文不丢，不用重开对话，本地工具完全不受影响**。

**只有两种身份：Agent 侧 / 桥接侧**（原来的「双侧」已取消，因为现在任何身份都能同时连接多个设备、也能同时被多个设备连接——身份只决定默认姿态，不再限制功能）：

| 身份 | 开机后 | 可被连接 | 默认 |
|---|---|---|---|
| **Agent 侧** | 不监听 | 开启配对窗口后才可以 | ✅ 新安装默认 |
| **桥接侧** | 立刻监听并显示配对码 | 可以 | |

身份与「可被发现」会**记住**（`$DSH_HOME/lan-bridge/prefs.json`），重启后保持。

**多设备与中转**：可以同时连接多个设备，也可以同时被多个设备连接，工具用 `device` 参数区分。而且支持中转——A 连接 B、B 连接 C，则 A 可以直接调用 C 的工具，**权限取两跳的最小值**（A 对 B 的权限 ∩ B 对 C 的权限）。

当前版本是 **跨版本临时方案**：Agent 侧跑 0.1.5，桥接侧跑 0.2.0。两边用的是**同一个包、同一份代码、同一套协议**，身份只是运行时选择。


---

## 0. 你手上有什么

```
dist/dsh-lan-bridge-0.2.0/     ← 在 DSH 0.2.0 上安装（macOS 用这个）
dist/dsh-lan-bridge-0.1.5/     ← 在 DSH 0.1.5 上安装（Windows 社区版用这个）
```

两个文件夹里的**插件代码完全相同**（构建脚本会校验），只有安装方式不同。包里没有 npm 依赖：只用 Node 内置模块，**不需要联网、不需要编译**。

---

## 1. macOS（DSH 0.2.0）安装 —— 用「从文件夹导入」

1. 把 `dsh-lan-bridge-0.2.0` 整个文件夹拷到 Mac 上，例如 `/Users/你的用户名/dsh-lan-bridge`。
   - 路径必须是 **POSIX 绝对路径**（以 `/` 开头），不要带 `~`。
   - 文件夹名随便，但里面的 `package.json` 名字必须是 `dsh-lan-bridge`（别改）。
2. 打开 DSH 0.2.0 → 左侧边栏底部找到 **「插件」** 页（面板 id 是 `plugins`）。
3. 点 **添加插件**。
4. 在 **「包名或地址」** 输入框里粘贴这个文件夹的**绝对路径**，例如：
   ```
   /Users/你的用户名/dsh-lan-bridge
   ```
   （界面里的示例就是 `/Users/name/my-plugin` 这种形式；0.2.0 没有单独的「从文件夹导入」按钮，这个输入框就是入口。）
5. **安装源** 这一项对本地目录没有影响，保持默认即可。
6. 点 **安装** → 会依次显示「正在检查…」「插件安装中…」→ 「已安装」。
7. 安装完默认是**未启用**状态，点 **立即启用**。
8. **重启 DSH**（退出整个 App 再打开）。刷新页面不够：主机侧插件代码由进程加载，必须重启进程。

> 如果安装时报 `incompatible-version`：本包的 `package.json` **刻意不声明任何 `@deepseek-ai/dsh*` 的 peer 依赖**，所以 0.1.5 与 0.2.0 都不会拒绝它。出现这个错误说明包被改过，请用原始包重新安装。

## 2. Windows（DSH 0.1.5 社区版）安装

0.1.5 **没有**插件管理界面（它的插件清单页是只读的），所以用 profile 依赖的方式安装。假设：

- DSH_HOME = `C:\Users\<你>\AppData\Roaming\DeepSeek Harness\dsh-home`
- 插件目录 = `H:\mod\dsh-lan-bridge`（或 `dist\dsh-lan-bridge-0.1.5` 的路径）

**如果你就是用本次交付的机器**：已经装好了，跳过本节，直接看第 3 节。

手动安装三步：

1. 编辑 `%DSH_HOME%\profiles\web\package.json`，在 `dependencies` 里加一行，并在 `dsh.profile.bundles` 末尾加一项：

   ```json
   {
     "dependencies": {
       "dsh-lan-bridge": "link:H:/mod/dsh-lan-bridge"
     },
     "dsh": {
       "profile": {
         "bundles": ["...原来的...", "dsh-lan-bridge"]
       }
     }
   }
   ```

2. 在 profile 目录里让 pnpm 建立链接（DSH 自带 pnpm，也可用系统 pnpm）：

   ```powershell
   cd "$env:APPDATA\DeepSeek Harness\dsh-home\profiles\web"
   pnpm install
   ```
   或者直接用 DSH 自己的命令（等价）：
   ```powershell
   dsh plugin --profile web add "H:/mod/dsh-lan-bridge"
   ```

3. **重启 DSH 0.1.5。**

> 卸载：把上面加的那行依赖与 bundles 项删掉，再 `pnpm install`，重启。

## 3. 连起来（两台机器）

两边都重启后：

### 桥接侧（被操作的那台，例如 Mac）
1. 打开侧边栏左下角的 **连接** 按钮（在「设置」旁边，图标 + 状态点）。
2. 身份选 **桥接侧**（只有两个选项：Agent 侧 / 桥接侧）。选完会**记住**。
3. 面板顶部会立刻显示一个 **6 位配对码**。把这 6 位数字念给 / 发给 Agent 侧的人。
   - 配对码是一次性的，10 分钟有效；用掉了或过期了就点 **刷新配对码**。

### Agent 侧（发起操作的那台，例如 Windows）
4. 身份选 **Agent 侧**（默认就是）。
5. 点 **刷新扫描**，列表里会出现桥接侧设备（名字、系统、身份、地址）。
   - 对方如果是 Agent 侧且没开配对窗口，这一行会**置灰并写明原因**，点不动——这不是 bug，是对方现在不接受连接。
   - 扫描不到就用手填地址：`192.168.10.8:47654`。
6. 点该设备的 **连接**，第一次需要填入第 3 步拿到的 **6 位配对码**。

### 桥接侧再确认一次
7. 桥接侧右上角会弹出一条**通知卡片**（面板关着也会弹，和系统通知一样）：显示设备名、**安全码**、以及可编辑的授权项：
   - **允许的根目录**（默认是当前工作目录）——远程只能在这几个目录里读写
   - **允许写入**、**允许执行 Shell**（默认关闭，按需打开）
   - **允许中转**（默认开）——允许对方通过本机到达本机能到达的设备；可以再限定为只允许某几个设备
   - 超时与输出上限
   - **记住此设备**（下次免配对码）
8. 核对 **安全码**：两台机器上显示的 6 位安全码**相同**才说明中间没有人冒充。核对无误后点 **同意**。

连上之后，Agent 侧的 AI 立刻多出 6 个工具，**标准模式、PTC 模式、创造模式、极简模式都会自动出现**（工具注册在宿主平面，不依赖某个预设）：

| 工具 | 作用 |
|---|---|
| `bridge_status` | 所有可达设备、连接状态、授权摘要、往返延迟 |
| `bridge_fs_list` | 列对端目录 |
| `bridge_fs_read` | 读对端文件（行号 / 偏移） |
| `bridge_fs_write` | 写对端文件（原子写） |
| `bridge_fs_edit` | 精确字符串替换编辑（与本地 edit 同语义） |
| `bridge_shell` | 在对端执行命令（Windows 走 pwsh/powershell，macOS/Linux 走 /bin/sh） |

这 6 个工具都接受一个可选的 **`device`** 参数：只连了一台设备时可以省略；连了多台时省略会得到一条列出所有设备的错误，模型据此选择。中转来的设备在结果里会标明经由哪台机器。

另外还有 5 个**控制面工具**（不碰任何远程文件，只在桥接「在用」时出现）：

| 工具 | 作用 |
|---|---|
| `bridge_devices` | 局域网里有什么、已连了什么、谁在请求连接 |
| `bridge_connect` | 主动连接某台设备（`deviceId` 或 `host`+`port`，可带配对码） |
| `bridge_pair` | 开启配对窗口并读出 6 位配对码 |
| `bridge_approve` | 同意/拒绝一个待处理的连接请求 |
| `bridge_disconnect` | 断开某台设备或全部 |

### 只有终端的时候（极简模式 / 无界面）

极简模式是「只有一个持久 Shell」的 Agent 预设，浏览器面板仍然在，所以上面那套照常可用。真正**只有终端**时，面板和通知卡片都不存在，此时**上面 5 个控制面工具就是全部界面**：

1. 让 Agent 调用 `bridge_pair` 拿到 6 位配对码；
2. 让 Agent 调用 `bridge_devices` 看到谁在请求连接（含安全码）；
3. 核对安全码后让 Agent 调用 `bridge_approve` 同意。

对方请求连接时，宿主日志里也会**大声打印**一条包含设备名、安全码和「怎么同意」的提示，这是无界面环境下唯一的通知面。如果对方在局域网里发现不到（组播被挡），在 profile 的插件行配置里加 `controlTools: always`，这 5 个工具就会一直在。

### 断开
- 任意一侧点 **断开**（或让 Agent 调 `bridge_disconnect`）。Agent 侧会**立刻回收这 6 个工具**，恢复成原来的样子；
  会话上下文保留，本地工具照常可用，**不需要重开对话**。
- 断开一台设备**不影响**其他设备：连了两台就断一台，另一台照常工作。
- 桥接侧可以随时 **撤销授权**（同时清除记忆的信任），该设备的连接会被立即断开。

## 4. 权限是怎么继承的

Agent 侧的每一个远程工具都会先看**本会话自己的权限设置**：

- 会话处于 **完全访问**（`danger-full-access`）→ 直接执行（因为本机已经被授权可以碰整台机器）。
- 否则 → 通过 DSH 的审批通道**逐次询问**；`ask` 策略会弹审批，批准一次执行一次。
- 审批策略是 **never**（本会话就是这么配的）→ 审批通道会确定性拒绝，于是工具返回一条**可读的拒绝原因**，提示你切换权限预设，而**不会静默绕过**。

另外，桥接侧自己的授权表永远是最终权威：即使 Agent 侧是完全访问，只要桥接侧没给 Shell 权限，`bridge_shell` 依然会被拒绝。

### 中转时权限怎么算（A → B → C）

A 调用 C 的权限是**两跳的最小值**，两边都通过才通过：

- **能力**：`允许写入` / `允许执行 Shell` 取交集——A 对 B 没给写，即使 B 对 C 给了写，A 也写不了 C；反过来同样成立。
- **上限**：超时、输出上限取更小的那个。
- **目录**：生效的是 **C 上的根目录**（B 对 C 的授权），因为 A 对 B 的授权里那些路径是 B 机器上的路径，对 C 没有意义。所以近端那一跳只能**收窄**，永远不能**放宽**远端。

另外 B 的授权里有一个 **允许中转** 开关（默认开），关掉后 A 完全看不到 C；也可以把 `relayPeers` 设成某几台设备，只允许中转那几台。

链路上每个节点都会往请求里追加自己的身份（`$relay.path`），**发现自己在路径里就拒绝**（防环），并且有跳数上限（默认 3 跳）。中转来的设备在工具结果里会标明经由哪台机器——这是安全相关的事实，不是装饰。

## 5. 安全设计（要点）

- **传输**：TCP + 长度前缀分帧，帧上限 8 MiB，超限即断连并毒化解码器。
- **握手**：双方长期 Ed25519 身份 + 一次性 X25519 临时密钥；首次配对用 **SPAKE2(P-256)**，因此**没有针对 6 位配对码的离线爆破**（这正是不能用「ECDH+HMAC(码)」的原因：中间人自己知道 ECDH 秘密，就得到了一份离线验证器）。
- **会话加密**：HKDF-SHA256 派生双向密钥，AES-256-GCM，nonce 由计数器派生（不取自网络），64 帧滑动重放窗口，定期 rekey。
- **信任**：首次配对后按设备固定公钥（TOFU）；已知设备的公钥变了会被**拒绝**，绝不自动改钉。
- **配对码**：一次性（任何失败都会作废该窗口），5 次尝试上限 + 递增冷却 + 硬锁定。
- **路径**：先做形状检查（NUL、`\\?\`、UNC、`C:foo`、NTFS 数据流 `f:s`、Windows 保留设备名 CON/PRN/NUL…），再 `realpath` 到最深的已存在祖先，最后做**分隔符感知**的前缀比较——符号链接逃逸、`..` 逃逸、盘符相对路径都挡在外面。大小写只在真正大小写不敏感的文件系统上折叠。
- **Shell**：默认关闭；以当前用户身份运行，cwd 锁在授权根内，超时**杀整棵进程树**，输出上限截断；另有少量「绝不该出现在调试里的」灾难性命令硬拒绝。
- **审计**：桥接侧把每一次允许/拒绝（含原因、字节数、耗时）追加到 JSONL，界面可见。
- **中转**：`$relay.path` 由每一跳追加，任一节点发现自己已在路径中就拒绝（`relay-loop`），超过 `maxHops`（默认 3）拒绝（`relay-limit`），转发前先把 `$relay` 从参数里剥掉，任何执行器都看不到它。近端授权只能收窄远端授权，不可能放宽。中转开关默认开，但可以按设备关掉或限定白名单。
- **UI 通道**：面板走 DSH 自己的连接 RPC（已有 Host/Origin 围栏）；另一条自带 token 的 HTTP 路由只作为兜底，token 每次启动随机生成、只注入到已被 DSH 围栏保护的页面里，并要求自定义头 + 同源 fetch 元数据。

## 6. 已知限制

- **本次未在真实 macOS 上运行过**（没有 Mac）。代码是零依赖纯 Node，Windows 上跨应用验证 + 线路层用例全绿；macOS 上需要留意：首次使用时的 **「本地网络」权限弹窗**（拒绝是静默的：socket 能建但收不到任何包，需要在 系统设置 → 隐私与安全性 → 本地网络 里放行后重启 App），以及 `/bin/sh`、进程组杀掉、APFS 大小写探测这几个平台分支。
- **必须重启（本次修了一个会把 DSH 整个搞崩的缺陷）**：上一版的 `FrameLink` 在 socket 出错时调用 `emit('error')`，而握手期间还没有任何监听者——Node 把「无监听者的 error 事件」当未捕获异常抛出，于是**整个 DSH 宿主进程退出（code 1），所有会话一起停摆**。已修：`FrameLink` / `Session` / 监听服务都在构造时自带兜底监听，四个 socket 回调与两个定时器也都在边界处兜住，任何回调抛出都不会再逃逸成未捕获异常；回归探针 `node _test\crash-smoke.mjs` 的断言就是「进程还活着」。**这个修复只在重启后生效**——插件代码在 DSH 启动时载入内存，改盘上的文件不会影响正在跑的进程。
- **升级注意**：身份现在是**持久化**的，但这一版之前的安装没有存过身份，所以升级后本机身份会回到默认值 **Agent 侧**。桥接侧那台（Mac）升级后需要**重新选一次「桥接侧」**，之后就记住了。如果没选，Agent 侧会看到它被置灰并写明「Agent 侧 · 未开启配对窗口」，不会出现莫名的连接超时。
- **`tool-addition` 提示**：DSH 0.2.0 在工具增减时会往对话里追加一条 `tool-addition` / `tool-removal` 开发者消息；**0.1.5 没有这个机制**，它只是在下一个 step 重新组装工具目录。两边都不需要重启、不需要重开对话、上下文不丢——0.1.5 只是少了一条显式提示。这一点已在本机实测过（注册后下一个 step 即可调用；回收后调用得到干净的 `unknown tool` 错误）。
- 同一台机器上同时跑两个实例时，第二个实例的 TCP 端口会从 47654 退让到随机端口（发现报文里会广播真实端口，正常工作）。
- 大文件传输目前是「整块读 + 上限截断」，没有流式分块；Shell 输出也是上限截断。
- 桥接侧的信任文件 `trust.json` 以 0600 保存长期私钥，没有接系统钥匙串。
- 中转链路上的每一跳都是**独立会话**，端到端没有额外的整体加密层：A→B 和 B→C 各自加密，B 能看到明文。这是「B 是受信任的中转者」这一前提的直接后果。
